# Налаштування безпеки CoreCommerce — інструкція для чайника

Ця інструкція проведе вас через увімкнення захисту сайту крок за кроком,
у правильному порядку. **Не пропускайте кроки і не міняйте порядок** —
неправильна послідовність (особливо для HTTPS/HSTS) може заблокувати
доступ до власного сайту.

---

## Частина 1 — SSL-сертифікат (HTTPS)

### Що це і навіщо

HTTPS шифрує з'єднання між браузером клієнта і вашим сервером. Без нього
паролі, дані карток, cookies передаються відкритим текстом — будь-хто в
тій же Wi-Fi мережі може їх перехопити.

### Крок 1.1 — Отримати SSL-сертифікат

**Якщо у вас реальний хостинг (не OSPanel):**

Більшість хостингів мають безкоштовний **Let's Encrypt** сертифікат в
панелі керування (cPanel, ISPmanager, Plesk):

1. Зайдіть в панель хостингу
2. Знайдіть розділ "SSL/TLS" або "Захищені з'єднання"
3. Натисніть "Отримати безкоштовний SSL" (Let's Encrypt)
4. Зачекайте 5-15 хвилин на активацію

**Якщо тестуєте локально на OSPanel:**

OSPanel вже має самопідписаний SSL для доменів `.test` — HTTPS має
працювати одразу на `https://mysite.test`. Браузер покаже попередження
"з'єднання не приватне" — це нормально для самопідписаного сертифіката,
натисніть "Продовжити".

### Крок 1.2 — Перевірте що HTTPS працює

Відкрийте `https://ваш-домен.com` (або `https://mysite.test` локально)
**до** будь-яких налаштувань в адмінці. Сайт має відкритись без помилок
сертифіката (окрім локального попередження OSPanel).

⚠️ **Не переходьте до кроку 2, поки HTTPS не працює!**

## Частина 2 — Редирект на HTTPS

### Крок 2.1 — Увімкнути в адмінці

1. Адмінка → Налаштування → вкладка **Безпека**
2. Знайдіть перемикач **"Редирект на HTTPS"**
3. Увімкніть його, збережіть

### Крок 2.2 — Перевірте

Відкрийте `http://ваш-домен.com` (без "s") — має автоматично
перекинути на `https://`. Якщо сайт перестав відкриватись взагалі —
негайно вимкніть перемикач через БД:

```sql
UPDATE settings SET `value` = '0' WHERE `key` = 'https_redirect';
```

## Частина 3 — HSTS (примусовий HTTPS у браузері)

### Що це і чому це небезпечно поспішати

HSTS каже браузеру: "запам'ятай, що цей сайт працює ТІЛЬКИ через HTTPS,
на вказаний термін". Якщо ви увімкнете HSTS з довгим терміном (1 рік), а
потім SSL-сертифікат зламається чи закінчиться — **браузери відмовляться
відкривати сайт взагалі**, і виправити це швидко не вийде (запис живе в
браузері користувача, а не на вашому сервері).

**Тому HSTS вмикається поступово:**

### Крок 3.1 — Тестовий режим (5 хвилин)

1. Переконайтесь що крок 2 (HTTPS редирект) вже працює мінімум кілька днів без проблем
2. Адмінка → Налаштування → Безпека → **HSTS**
3. Увімкніть HSTS
4. Термін дії (`max-age`) — виберіть **"Тестовий режим — 5 хвилин"**
5. Збережіть

### Крок 3.2 — Перевірте протягом 5 хвилин

Відкрийте сайт через `https://`, потім спробуйте `http://` — має
перенаправити. Перевірте що все працює нормально: логін, кошик,
оплата.

### Крок 3.3 — Поступово збільшуйте термін

Якщо все ОК протягом кількох днів — збільшуйте термін дії поступово:

```
5 хвилин → 1 година → 1 день → 1 місяць → 1 рік
```

На кожному етапі чекайте хоча б добу-дві перш ніж збільшувати далі.

### Крок 3.4 — Preload (тільки для досвідчених, необов'язково)

"Preload" означає що ваш домен додається у вбудований список Chrome,
Firefox — браузери будуть вимагати HTTPS для вашого сайту **навіть
при першому відвідуванні**, без жодного запиту по HTTP.

⚠️ Увімкнення Preload — це **майже незворотна дія**. Видалення з
preload-списку займає місяці. Вмикайте лише коли:
- HSTS вже стоїть на "1 рік" мінімум кілька тижнів без проблем
- Ви на 100% впевнені що сайт завжди буде на HTTPS

## Частина 4 — CSP (Content Security Policy)

### Що це

CSP каже браузеру: "завантажуй скрипти/стилі/зображення тільки з цих
джерел". Захищає від XSS-атак — навіть якщо зловмисник впровадить
`<script>` через вразливість, браузер його заблокує.

### Крок 4.1 — Режим "Тільки звітування"

1. Адмінка → Налаштування → Безпека → **CSP**
2. Виберіть режим **"Тільки звітування (рекомендовано спочатку)"**
3. Збережіть

У цьому режимі CSP **нічого не блокує**, тільки показує в консолі
браузера (F12 → Console) що було б заблоковано.

### Крок 4.2 — Перевірте консоль браузера

Відкрийте кілька сторінок сайту (головна, товар, кошик, чекаут,
адмінка) з відкритою консоллю розробника (`F12`). Шукайте повідомлення
типу:

```
Content-Security-Policy: The page's settings blocked ...
```

Якщо бачите такі помилки — значить якийсь плагін або тема завантажує
щось із неочікуваного джерела. Повідомте про це технічну підтримку.

### Крок 4.3 — Активний захист

Якщо кілька днів тестування в режимі звітування не показали помилок:

1. Адмінка → Налаштування → Безпека → CSP
2. Виберіть **"Активний захист"**
3. Збережіть
4. Ще раз перевірте всі основні сторінки

## Частина 5 — Rate Limiting (захист від підбору паролів)

### Що це

Захищає форму входу від "brute-force" атак — коли зловмисник намагається
підібрати пароль перебором тисяч варіантів.

### Як це працює (вже увімкнено за замовчуванням)

- **10 невдалих спроб з одного IP** за 15 хвилин → блокування на 30 хвилин
- **5 невдалих спроб для одного email** за 15 хвилин → блокування на 30 хвилин

Нічого додатково налаштовувати не потрібно — це працює одразу з коробки.

### Якщо у вас Nginx reverse proxy або Cloudflare

Якщо ваш сайт стоїть **за проксі-сервером** (Cloudflare, Nginx як
reverse proxy перед Apache, load balancer) — потрібно вказати IP цього
проксі, інакше rate limiting не зможе визначити реальний IP атакуючого.

Відкрийте `config/security.php`:

```php
return [
    'trusted_proxies' => ['127.0.0.1'],  // ← IP вашого проксі-сервера
];
```

**Якщо не впевнені чи у вас є проксі** — залиште порожнім `[]`. Це
безпечний варіант за замовчуванням.

## Частина 6 — CSRF (захист форм від підробки запитів)

### Що це

Захищає від ситуації коли зловмисний сайт намагається відправити форму
"від вашого імені" (наприклад видалити товар в адмінці) поки ви
залогінені в CoreCommerce в іншій вкладці.

### Налаштування

**Нічого не потрібно робити** — CSRF-захист вбудований у всі форми
проекту автоматично. Кожна форма містить прихований токен, який
перевіряється на сервері.

Якщо після оновлення коду форма перестала зберігатись з помилкою
"CSRF токен недійсний" — очистіть кеш браузера і залогіньтесь заново
(токен прив'язаний до сесії).

## Підсумкова таблиця — правильний порядок

| # | Крок | Що перевірити перед переходом далі |
|---|------|--------------------------------------|
| 1 | SSL-сертифікат | `https://` відкривається без помилок |
| 2 | Редирект на HTTPS | `http://` автоматично веде на `https://` |
| 3 | HSTS — 5 хвилин | Сайт працює нормально 1-2 дні |
| 4 | HSTS — поступово збільшувати | Кожен крок тримати кілька днів |
| 5 | CSP — тільки звітування | Немає помилок в консолі браузера кілька днів |
| 6 | CSP — активний захист | Ще раз перевірити всі сторінки |
| 7 | Rate Limiting | Працює автоматично, налаштувань не потребує |
| 8 | CSRF | Працює автоматично, налаштувань не потребує |

## Що робити якщо щось зламалось

### Сайт взагалі не відкривається після HTTPS редиректу

```sql
UPDATE settings SET `value` = '0' WHERE `key` = 'https_redirect';
UPDATE settings SET `value` = '0' WHERE `key` = 'hsts_enabled';
```

### CSS/JS не завантажуються після увімкнення CSP

```sql
UPDATE settings SET `value` = 'off' WHERE `key` = 'csp_mode';
```

### Забанило власний IP через rate limiting під час тестування

```sql
DELETE FROM login_attempts WHERE ip = 'ваш_IP';
```

(Свій IP можна дізнатись на [whatismyip.com](https://www.whatismyip.com))
